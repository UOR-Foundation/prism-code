# prism-code v0.1.0 release runbook

This runbook takes prism-code from "PrismPM v0.4.0 and its template release
exist" to "prism-code `v0.1.0` is tagged, its Pages site serves the generated
closure, and its CLI binaries are attached to the GitHub release". It serves
[#26](https://github.com/UOR-Foundation/prism-code/issues/26), the milestone
tracking issue.

It is written against prism-code `main` at `75305b6d` (2026-10-22). Citations
use `path:lines` at that commit unless they name another repository or ref.
PrismPM citations at `main` are at `c1432003`; citations "on #227" are at that
pull request's head `6e2f526b`. A step that names a workflow or script that
later changes must be rechecked before it is run.

## What "released" means

- **Release policy.** "Each project makes the progress it needs by importing
  upstream commits between releases, but a release pins only upstream
  releases" (#26 body, "Release policy"). v0.1.0 is held until LexLean v0.4.0
  and PrismPM v0.4.0 are released and imported (#26 body; [#4](https://github.com/UOR-Foundation/prism-code/issues/4)
  body, "Release policy").
- **Tag condition.** "Tag `v0.1.0` when every box above is checked and every
  lock names only upstream releases (no commit pins): Pages is live from the
  tag's commit, the release carries both CLI binaries, `SHA256SUMS`, the SBOM
  and the design views, and `CONFORMANCE.md` is regenerated from the register"
  (#26 body, "Release").
- **Release binding.** `prismpm.lock` names the PrismPM v0.4.0 release SDK,
  `template.lock` names a template release, `prismpm template check` and
  `prismpm lock check` pass, and `just vv` passes in the pinned devcontainer
  (#4 body, "Acceptance criteria", release binding).
- **Upstream "done".** PrismPM's milestone closes when "a prism-code instance
  binds it in `prismpm.lock`, `just vv` passes in its devcontainer, and its
  Pages site and CLI are generated by the SDK" (PrismPM
  [#211](https://github.com/UOR-Foundation/PrismPM/issues/211) body, quoted in
  PrismPM `docs/release/v0.4.0-runbook.md`, "What released means").

`just vv` is `template-check fmt-check model lint test features bdd deny`
(`Justfile:6`). None of those recipes runs `prismpm check`, `build` or
`verify` (`Justfile:8-57`), so today a green `just vv` does not prove the
model builds ([PR #35](https://github.com/UOR-Foundation/prism-code/pull/35)
body, first paragraph). Steps 6, 7 and 10 below are where that evidence comes
from; step 6 is what makes `just vv` carry it.

### 12. Release workflow for the CLI binaries (#20) [member]

Nothing upstream covers this. The starter deploys Pages only; the reusable
`prismpm.yml` (`.github/workflows/prismpm.yml:170-243`) signs and pushes an OCI
release, not GitHub release assets; PrismPM's own `release.yml` is for
PrismPM. #20 asks for a `v*`-tag workflow that builds once through the shared
Action and attaches `prism-code-<version>-x86_64-unknown-linux-musl.tar.gz`,
`prism-code-<version>-aarch64-unknown-linux-musl.tar.gz`, `SHA256SUMS`, the
SPDX 3.0.1 SBOM and the design views, "one job per architecture, tags only"
(#20 body).

Two facts shape the skeleton: one `prismpm build` on one runner already
produces both musl programs, byte-identical across runs (PR #227 body,
"Evidence run locally", third bullet), but `application-acceptance` executes
only the host-architecture program (on #227 `SPEC.md:248-249`). So the
skeleton builds on both runners, has each runner package the program it
executed, cross-checks that both runners produced the same two digests, and
attaches everything in one release job. The skeleton below is to be landed by
#20's own PR; it is not part of this runbook's change. Its pins reuse the
commits already pinned in this repository's workflows and the starter.

```yaml
# .github/workflows/release.yml (skeleton for #20; adjust the build-id lookup
# to the fields of prismpm/build-result/1 once the SDK is bound)
name: release

on:
  push:
    tags: ['v*']

permissions: {}

concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false   # never cancel a release in flight

jobs:
  build:
    name: build and package / ${{ matrix.runner }}
    strategy:
      fail-fast: true
      matrix:
        include:
          - runner: ubuntu-24.04
            target: x86_64-unknown-linux-musl
          - runner: ubuntu-24.04-arm
            target: aarch64-unknown-linux-musl
    runs-on: ${{ matrix.runner }}
    timeout-minutes: 60
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
        with:
          fetch-depth: 0
          persist-credentials: false
      - id: lock
        shell: bash
        run: |
          set -euo pipefail
          image=$(sed -n 's/.*"sdk_image":"\([^"]*\)".*/\1/p' prismpm.lock)
          [[ $image =~ ^[a-z0-9.-]+(:[0-9]{1,5})?/[a-z0-9./_-]+@sha256:[0-9a-f]{64}$ ]]
          printf 'sdk-image=%s\n' "$image" >> "$GITHUB_OUTPUT"
      - uses: UOR-Foundation/PrismPM/action@<ACTION_REFERENCE commit> # prismpm-action-input
        with:
          command: fetch
          sdk-image: ${{ steps.lock.outputs.sdk-image }}
      - id: build
        uses: UOR-Foundation/PrismPM/action@<ACTION_REFERENCE commit> # prismpm-action-input
        with:
          command: build
```

## Decisions the release needs

1. **Where planted defects are recorded.** #8, #19 and #23 say "record it in
   `VERIFICATION.md`". That file is a universal policy path byte-bound by
   `template.lock` (`template-contract.json`, `universal_policy_paths`), and
   `AGENTS.md` ("SDK and template boundary") forbids editing a universal file
   for one repository's evidence. Pick a project-owned file
   (`TEMPLATE-VERIFICATION.md` is project-owned today, or a new
   `docs/verification.md`) and amend the three issues.
2. **`just vv` and the 45-minute bootstrap.** #13 puts `prismpm check`, `build`
   and `verify` into `just vv`; `bootstrap.yml` runs it on two runners with
   `timeout-minutes: 45` (`:19-21`) and cannot be edited here. If a full build
   plus Lean verification does not fit, the alternatives are a template change
   (the #25 proposal in PR #37's body) or running build and verify in a
   project workflow on `main` and tags only, which weakens "`just vv` is the
   complete acceptance boundary" (`AGENTS.md`). Measure once in the devcontainer
   before choosing.
3. **Release scope.** #26's tag condition names design views, but #24 (and
   #16, #22) is off the milestone; #15 waits for PrismPM #242; #25's "one CI
   job per PR" needs the template. Decide which of #15, #24 and #25 gate the
   tag.
4. **Lifecycle at the tag.** `Product.lifecycle` is `"development"` and the
   Pages target's `minimumReleaseStatus` is `"development"`
   (`src/System.lex.tex:13`). Decide whether v0.1.0 flips them and what
   `BrowserSystem::validateManifest` then requires.
5. **Who tags, and whether `template-update` gets a required reviewer.** No
   file names either; the defaults here are Ilya and no reviewer.
6. **Asset shape.** #20 names `.tar.gz` archives per target; the SDK emits raw
   `cli/bin/{target}/prism-code`. The skeleton packages them; confirm the
   names, and whether `application-acceptance.json` is attached as evidence.
